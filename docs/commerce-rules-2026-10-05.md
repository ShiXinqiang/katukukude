# 商品、商家、审核与订单规则（2026-10-05）

## 本次实施范围

实现实物商品的发布、SKU库存、配送、额外保障、审核、结算、发货和整单人工售后闭环。没有把在线收款、资金退款或实时物流查询伪装为已接入。酒店房态、服务预约时间库存、部分商品退款、自动退款渠道仍不在此版本范围内。

## 使用入口

- 商家后台 → 商品 → 发布商品：基本信息、规格库存、配送保障、预览提交。
- 商家后台 → 首页：待审核、在售低库存（少于5件）、待处理售后。
- 商家后台 → 商品：图片、搜索、分类/状态筛选、20件分页、批量提交审核/下架、拒绝原因。
- 商家后台 → 店铺：修改联系电话和介绍；认证主体/经营地址仍需平台核实。
- 管理后台 → 商品规则：维护1–50个分类，启停退货、破损补发、保修选项。
- 管理后台 → 全站商品管理：图片、说明、规格、配送保障审核，运营配置，最近50条商品操作记录。
- 我的订单 → 申请售后；商家后台/管理后台 → 售后处理。

## 强制规则

1. 草稿至少有标题；提交需要4字标题、10字说明、有效平台分类、至少1张有效图片、正售价、可售库存及配送信息。
2. 图片最多8张，可排序；上传进度按文件显示。内部图片必须归属当前店铺。外部地址只接受HTTPS。
3. 最多3组规格、每组20个值、总计100个组合；每个组合独立价格、库存、可选图片。总库存和起售价由组合汇总。
4. 金额最多2位小数，非负；售价必须为正；划线原价不得低于任一SKU售价。促销文案需对应有效起止时间。
5. 配送指定省邦、发货地点、付款后1–720小时内发货。买家结算选择支持省邦并自行核对详细地址。同店取最高运费，跨店相加；免运费仅适用所选地区。
6. 退货填时限、条件和运费承担方；破损补发填申请时限和凭证/处理要求；保修填期限、范围、联系方式。没有勾选不显示额外承诺，也不排除质量问题的售后处理。
7. 在售商品编辑保存后进入草稿或待审核，不能直接变更在售内容。审核中必须先撤回再修改。只有待审核商品可审核通过/拒绝，拒绝必须说明原因。
8. 官方标识只由管理员配置；运营配置与销售资料分开。客户端展示规则与服务端校验共用。
9. 更新时核对记录版本，防止覆盖新库存/新修改。商品修改、审核、规则变更、订单动作及售后处理记录审计。
10. 已有订单的商品不可删除；有未结束订单时不能改变规格组合。下架保留历史订单。
11. 报价和下单均校验商家/商品状态、规格、库存、地区和价格。报价摘要变化时需重新核对。客户端传入售价不作为结算依据。
12. 下单事务锁定商品，逐SKU扣库存；稳定结算键和数据库唯一索引防止重复提交。取消未付款订单仅返库存一次。
13. 下单将配送和售后条款写入订单快照，商品后续修改不覆盖历史承诺。旧订单没有快照时明确显示未记录，不追补虚构条款。
14. 人工确认收款必须金额准确、提供真实流水号，流水不可用于另一笔订单。此功能是收款登记，不是支付渠道。
15. 已付款才能接单；准备中才能发货；快递填写公司及单号，同城填写配送联系人及电话。买家实际收货后确认完成。
16. 售后申请仅限本人已付款订单，同一订单不能同时存在多笔进行中申请。商家可回复，平台批准/拒绝并说明处理方式。未结束售后阻止接单、发货或完成等履约推进。
17. 售后批准不改变付款状态。登记整单退款需要实际转账确认、足额退款金额和真实凭证。退货退款需确认收到退货；已发货商品只有确认退回且可再次销售才可勾选返库存。禁止重复退款/返库存。

## 数据兼容及运维

- 现有商品与订单未被批量修改、下架或删除。旧商品再次提交/审核时需补齐新版规则；旧的自由文本保障不冒充新版结构化条款。
- 新增 products.product_rules；orders.shipment/completed_at/checkout_key；commerce_settings、commerce_audit、after_sales 表。均在 lib/merchant.ts 中以幂等方式维护。
- 三张新表启用RLS，不向匿名/普通Supabase客户端提供直接访问策略。项目通过现有服务端Postgres连接及应用权限控制访问。
- Supabase安全检查仅返回RLS启用但无策略的INFO，与现有服务器专用访问架构一致，不为消除提示而开放访问。说明：https://supabase.com/docs/guides/database/database-linter?lint=0008_rls_enabled_no_policy
